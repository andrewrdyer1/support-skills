Finding a customer

Your first day as a support engineer at Paperkite, an invoicing app for small businesses. A ticket is waiting. You'll answer it by asking the database, not by guessing.

Ticket #1151 · account access · open

From maya@harborandpine.com · Oct 30, 1:12 PM

Hi, we added our new bookkeeper Sam to the team ten days ago and he says he never got an invite email. He's checked spam. Can you look into it? He needs to get into the invoices before month end.

A support agent would reply "please try resending the invite." A support engineer finds out what actually happened. By the end of this lesson you'll know, and you'll have learned the SQL that most support jobs use every day.

How this course works

Every grey box with a Run button is a real query against a real Postgres database running on your Mac. Edit anything and run it again. You can't break it: your access is read-only, and a query that runs longer than 5 seconds is stopped.

Exercises have a Check button that compares your result with the answer. There's usually more than one correct way to write it.

1. A database is a set of strict spreadsheets

A database is a collection of tables. A table is like a spreadsheet tab, with one big difference: every column has a fixed name and a fixed type. A created_at column holds timestamps and nothing else. An id column holds whole numbers. You can't type "TBD" into either.

Each row is one thing: one account, one user, one invoice. Paperkite's database has eight tables:

TableOne row is…Columns you'll use most
accountsa business paying for Paperkiteid, name, plan_id, status, country, created_at
usersa person who can log in to an accountid, account_id, email, full_name, role, last_login_at
plansa price planid, name, monthly_price_cents, api_access
clientsa business the customer sends invoices toid, account_id, name
invoicesone invoiceid, account_id, number, status, amount_cents, issued_at, paid_at
ticketsa support ticketid, account_id, requester_id, subject, category, priority, status, created_at
api_keysa key a customer uses to call the APIid, account_id, label, scopes, revoked_at
eventssomething a user did, like logging inid, account_id, user_id, name, created_at

Notice how many tables have an account_id column. That's how the tables connect: a user row with account_id = 1 belongs to the account whose id is 1. An id that identifies a row is its primary key. A column that points at another table's id, like account_id, is a foreign key. Keep that in mind; it's the whole idea behind section 7.

2. SELECT: show me some rows

Every query in this lesson starts with SELECT. Run this one:

Read it as a sentence: show every column (*) from the accounts table, but only 5 rows.

  • select says which columns. * means all of them.
  • from says which table.
  • limit caps how many rows come back. Get in the habit: on a real production database a table can have millions of rows, and an unlimited query is slow for you and for everyone else using it.
  • Keywords aren't case-sensitive. SELECT, select and Select all work. Many people capitalize keywords to make them stand out; this course uses lowercase. Pick one and be consistent.
  • The semicolon ends the statement. Most tools don't need it for a single query, but it's a good habit.

3. WHERE: only the rows I care about

where filters rows. It comes after from:

Three things trip up everyone at first:

  • Text goes in single quotes: 'past_due'. Double quotes mean something else in SQL (a column name), so "past_due" gives you an error about a column that doesn't exist.
  • Numbers don't: where id = 1.
  • Text matching is exact. 'Past_Due' matches nothing. Section 4 shows how to match loosely.

The comparison operators are what you'd expect:

On the job

Search wide, then narrow. When you're looking up a customer, start with the loosest match that makes sense (ilike '%harborandpine%'), see what comes back, then tighten. Starting exact is how support people end up telling a customer "you don't have an account" when they do.

Zero rows, and no error. In SQL, null means "unknown," and comparing anything to an unknown gives unknown, which where treats as "no." Even null = null isn't true. You have to ask specifically:

is null and is not null are the only reliable ways to test for it. Write them often: null columns are everywhere in support work. "Never logged in," "no reply yet," "not paid," "not canceled" are all nulls.

A ticket has first_response_at = null. What does that mean?

Nobody has replied to it yet. That's a very common support query: where first_response_at is null and status = 'open' is "tickets still waiting for a first reply."

6. ORDER BY: put them in order

Rows come back in no particular order unless you ask for one. Postgres is free to return them however is fastest, and that can change from one run to the next. If order matters, say so:

desc means descending: newest first, biggest first, Z to A. asc (ascending) is the default. You can sort by more than one column: order by plan_id, name sorts by plan, then alphabetically within each plan.

Order of the clauses matters, and it's always this:

select … from … where … order by … limit …

LEFT JOIN: keep rows even when there's no match

A plain join only keeps rows that found a partner. An account with no API keys disappears from accounts join api_keys entirely, because there's nothing to pair it with. Often that's what you want. Sometimes the missing ones are the whole point: "which customers haven't set up X?"

left join keeps every row from the left-hand table (the one after from) and fills the right-hand columns with null when there's no match:

8. Back to the ticket

You've seen everything you need. Look at Sam's row one more time:

What happened to Sam's invite?

Sam's user was created on Oct 20, exactly when Maya said, so the invite did go out. But it went to sam@harborandpine.co, missing the "m". Everyone else on the team is at .com. The invite was sent to an address nobody reads, which is why Sam never saw it, and why last_login_at is still null.

Notice that the exact search in section 4 (like '%@harborandpine.com') missed him completely. If you'd stopped there, you'd have told Maya that Sam wasn't on the account at all.

Before you reply, check whether Harbor & Pine has anything else open. Customers appreciate it when you notice:

There's a second open ticket, about the CSV export. Hold that thought: it's the whole of Lesson 6.

The reply

A good support reply leads with the answer, gives one clear fix, and quotes their own details back so they can see you looked:

Hi Maya, I found it. Sam's invite went to sam@harborandpine.co (no "m" at the end), so it never reached him. If you remove that user under Settings → Team and invite sam@harborandpine.com, the new invite should arrive within a minute. I'll keep this ticket open until he's in. I also see your note about the CSV export. I'm looking into that one separately and will update you there.

Why you didn't just fix it

You could only read. In a real job you'll sometimes have write access, and the rule is: never change customer data with a hand-typed query if there's a tool or an admin page that does it. The tool checks things your query won't (sending the new invite, writing an audit log). The most famous mistake in SQL is an update users set email = '…' without a where, which changes every user's email at once. Lesson 3 is about doing it safely when you have to.

9. Doing this in a real terminal

Many support teams query a read-only copy of production with psql, the command-line tool that comes with Postgres. The same database you've been using is waiting there. In Terminal:

psql "postgresql://learner@localhost:5488/paperkite"

Then type a query and end it with a semicolon. A few commands that start with a backslash belong to psql itself, not SQL:

CommandWhat it does
\dtlist the tables
\d usersdescribe a table: its columns and their types
\xtoggle "expanded" display, one column per line; good for wide rows
\qquit

Try \d invoices. Knowing a table's exact column names and types before you write a query saves a lot of guessing.

Recap

  • select columns from table where conditions order by column limit n, in that order.
  • Text in single quotes. Use ilike '%piece%' to search loosely.
  • and binds tighter than or; use parentheses.
  • null means no value. Test it with is null, never = null.
  • join … on pairs rows across tables; left join keeps the rows with no partner, so you can find what's missing.
  • Search wide, then narrow. Read the data before you answer the customer.
Interview prep

Support engineering interviews often include a short live SQL exercise. The questions look a lot like this lesson: "find the customers who…", "which accounts have no…", "why does this query return nothing?" (the answer is very often = null, or a missing parenthesis around an or). Talk out loud as you go. Saying "I'll start loose and narrow down" is exactly what they want to hear.
