1. Aggregates: one answer from many rows

An aggregate function takes a whole column of values and squashes it into one. The one you'll use most is count:

One row, one number: every ticket ever. Add a where and it counts only the rows that pass the filter. The other aggregates work the same way:

FunctionGives you
count(*)how many rows
count(column)how many rows where that column is not null
count(distinct column)how many different values
sum(column)the total
avg(column)the average (mean)
min(column), max(column)the smallest and largest; work on dates too (earliest, latest)

The difference between count(*) and count(column) is worth seeing once:

count(first_response_at) skips the nulls, so it's "tickets that got a reply." The gap between the first two numbers is the tickets still waiting. And as gives a column a readable name, which matters as soon as anyone else reads your results.

Aggregates skip nulls in general: avg(x) is the average of the rows that have an x. Usually that's what you want. Just know it's happening.

2. GROUP BY: one answer per group

"How many tickets per category?" needs a count for each category, not one overall. group by splits the rows into piles, one per distinct value, then runs the aggregate on each pile:

The rule that makes group by click: every column in your select must either be in the group by or be inside an aggregate. Try adding priority to the select list above without grouping by it, and read the error. Postgres is saying "you made one row per category; which of that category's many priorities should I show?" Either group by it too (one row per category and priority), or aggregate it.

HAVING: filtering the groups

where filters rows before they're grouped. To filter on the result of an aggregate (only categories with more than 100 tickets, only customers with 5 or more), you need having, which runs after grouping:

The full order of clauses is now:

select … from … join … where … group by … having … order by … limit …

And joins work exactly as before. Join accounts to show names instead of ids, then group by the name.

3. Averages, rounding, and the integer trap

Before dates, one trap that catches everyone computing a percentage:

Divide one whole number by another and Postgres gives you a whole number, throwing the remainder away. 1 / 2 is 0. Counts are whole numbers, so count(*) filter (…) / count(*) is almost always zero. Put a decimal in (100.0 *) and the math stays decimal. round(value, 1) keeps one decimal place.

4. Dates and times

Support data is full of timestamps: when a ticket arrived, when someone replied, when it was solved. Here's what you need.

Filtering by date

Write a date as text in YYYY-MM-DD form and Postgres converts it. For a date range, the safest pattern is "on or after the start, strictly before the day after the end":

Why not between?

created_at between '2026-10-01' and '2026-10-31' looks right and is wrong. '2026-10-31' means midnight at the start of the 31st, so every ticket from the 31st after 12:00 AM is left out. The "before the next day" pattern can't make that mistake.

An interval reads nicely but you can't average it into "hours" directly. To get a plain number, pull the seconds out with extract(epoch from …) and divide by 3600:

You can also compare against an interval directly: first_response_at - created_at <= interval '4 hours'. And you can do arithmetic with one: now() - interval '7 days' is "a week ago," which is how real reports usually say "this week."

5. CASE: your own categories

case is SQL's if/else. It checks conditions in order and gives back the value for the first one that's true:

Order matters: a 30-minute wait passes the second test and stops there, so it's never labeled "1 to 4 hours." Put the null check first, because a null passes none of the comparisons and would fall through to else.

Recap

  • count(*) counts rows; count(column) skips nulls; count(distinct …) counts different values.
  • group by makes one row per group. Everything you select is grouped or aggregated.
  • where filters rows before grouping; having filters groups after.
  • Whole number ÷ whole number = whole number. Use 100.0 * for percentages.
  • Date ranges: >= start and < day after end. Subtracting timestamps gives an interval; extract(epoch from …) / 3600 turns it into hours.
  • case when … then … end makes your own categories; count(*) filter (where …) counts a subset alongside the total.
Interview prep

A favorite interview question: "What's the difference between WHERE and HAVING?" Your answer: WHERE filters individual rows before they're grouped; HAVING filters the groups afterwards, so it's the only one that can use an aggregate like count(*). Another: "Why does this percentage come out as 0?" (integer division).
