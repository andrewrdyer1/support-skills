What a web page is made of

Customers describe problems by what they see on screen. To get from "the button's gone" to "this element has display: none," you need to know what a page is built from and how to look inside one.

New ticket · bug · normal

From maya@harborandpine.com

Small thing, but our overdue invoices don't show the red "overdue" label anymore. The paid ones still say paid. Makes it hard to see who to chase.

You'll fix nothing in this lesson. You'll learn enough HTML and CSS to read a page, then open the real Paperkite page in your browser's developer tools and find exactly why that label disappeared, so the engineer who fixes it doesn't have to.

1. Three languages, three jobs

Every web page is built from three languages working together:

LanguageIts jobAnalogy
HTMLWhat's on the page: headings, text, links, tables, buttonsThe walls and rooms of a house
CSSHow it looks: colors, sizes, spacing, layoutPaint and furniture
JavaScriptWhat it does: load data, react to clicks, show errorsThe wiring and plumbing

When a page loads, the browser reads the HTML and builds a tree of elements in memory called the DOM (Document Object Model). CSS decides how each element in the tree looks. JavaScript can add, change or remove elements in the tree at any time. That's how Paperkite's invoice table fills itself in after the page loads.

2. HTML: elements, tags and attributes

HTML is made of elements. Most elements have an opening tag, some content, and a closing tag with a slash:

<p class="note">Payment is due in 30 days.</p>
 ↑    ↑                                  ↑
 tag  attribute                          closing tag

Attributes go inside the opening tag and add information: class labels an element for styling, href is where a link goes, src is an image's file. Elements nest inside each other, which is what makes the tree.

3. class and id: names for elements

Two attributes matter more than the rest, because CSS and JavaScript use them to find elements:

  • class="badge paid" gives an element one or more labels, separated by spaces. Many elements can share a class. This element has two classes: badge and paid.
  • id="export" gives one element a unique name. Only one element on a page should have a given id.

Hold onto "separated by spaces." It's at the center of this lesson's ticket.

4. CSS: rules, selectors and properties

CSS is a list of rules. Each rule says which elements (the selector) and how they should look (a list of property: value; pairs):

.badge.paid {             ← selector: elements with class badge AND class paid
  background: #1f8a52;    ← property: value;
  color: white;
}
SelectorMatches
pevery <p> element
.badgeevery element with class badge
.badge.paidelements with both classes (no space between them)
#exportthe element with id export
.card pany <p> anywhere inside a .card (a space means "inside")
a:hovera link while the mouse is over it

Properties you'll see constantly: color (text color), background, font-size, font-weight, margin, padding, border, display, width. Colors are written as names (red), hex codes (#c62f24), or rgb(198, 47, 36). DevTools usually shows them as rgb.

The box model

Every element is a rectangle made of four layers, from the inside out:

┌──────────── margin ────────────┐   space outside the border, pushing neighbors away
│ ┌────────── border ──────────┐ │   the visible edge
│ │ ┌──────── padding ───────┐ │ │   space inside the border, around the content
│ │ │        content         │ │ │   the text or image itself
│ │ └────────────────────────┘ │ │
│ └────────────────────────────┘ │
└────────────────────────────────┘

When something on a page is "too cramped" or "has a weird gap," it's almost always padding or margin. DevTools draws this exact diagram for any element you select.

display and layout

display decides how an element takes up space. The values worth knowing:

  • block: starts on a new line and stretches the full width (div, p, h1).
  • inline: flows inside a line of text (span, a, strong).
  • none: not shown at all, and takes up no space. The number one answer to "where did the button go?"
  • flex: lays out its children in a row (or column) with control over spacing and alignment. Most modern layouts are built with it.

The cascade: why a style "doesn't apply"

When two rules set the same property on the same element, CSS has to pick one. The rule with the more specific selector wins: an id beats a class, and a class beats a plain element name. Only when they tie does the rule written later win.

This is behind a lot of "I changed the color and nothing happened." In DevTools, the losing rule shows up with a line through it.

CX operations note

Help center articles, saved replies (macros) and email templates are usually HTML with a little CSS. Email is a special case: many email apps strip out <style> blocks, so email HTML puts its styles directly on each element (<p style="color: #555">) and often uses tables for layout. If a template looks fine in the editor and broken in Outlook, that's usually why.

5. DevTools: looking inside any page

Every desktop browser ships with developer tools that show the live HTML, CSS, JavaScript errors and network traffic behind the page you're looking at. For a support engineer, this is the single most useful tool there is.

Open the Paperkite app in a new tab: localhost:4747/portal.html. It's Harbor & Pine's invoice page. Then open DevTools:

BrowserShortcut
Chrome, Edge, Arc, Brave⌘ ⌥ I (Mac) or F12 (Windows)
SafariFirst turn on Settings → Advanced → "Show features for web developers", then ⌘ ⌥ I
Firefox⌘ ⌥ I

Or right-click anything on the page and choose Inspect, which opens DevTools with that element already selected. The three tabs that matter:

  • Elements (Safari: Elements; Firefox: Inspector): the live DOM. Click an element to see every CSS rule that applies to it, which ones lost (crossed out), and the final Computed values. You can edit HTML and CSS right there to test a fix. Changes vanish when you reload; nothing is saved.
  • Console: JavaScript errors and messages. A red line here is often the whole story behind "the page doesn't work."
  • Network: every request the page makes to a server, with its status code and response. Lesson 5 is about what those requests are.

Find the missing label

In the Paperkite tab, find a row whose status cell looks empty. That's an overdue invoice. Right-click the empty-looking spot in the Status column and choose Inspect. Look at the selected <span>: its text is there, so the HTML isn't missing anything. Now look at its classes, and compare them with the CSS rules in the Styles panel.

Why is the text there but invisible?

The base .badge rule sets color: #ffffff (white text) and expects each status rule to supply a colored background. The overdue badge has the classes badge and overdeu. There's no .badge.overdeu rule, so it gets white text on no background: white on a white table. In the Computed panel, color is rgb(255, 255, 255) and background-color is transparent.

Try the fix live: in the Elements panel, double-click overdeu in the class attribute, change it to overdue, and press Enter. The red label appears. That's the proof you'd put in a bug ticket.

What you'd send engineering

Overdue badges render blank on the Invoices page. The span gets class overdeu (typo) instead of overdue, so the .badge.overdue rule never matches and the text is white on white. Changing the class to overdue in DevTools fixes it. Likely the status-to-class map in the invoices page script. Affects every account; cosmetic, but customers use it to find who to chase.

Compare that with "customer says the overdue label is missing." The engineer can fix the first one in five minutes.

The Console and the Network tab

Now click Export CSV on the Paperkite page. You'll get the same "Something went wrong" message Maya saw.

Switch to the Console tab: there's a red Export failed 500 line the page wrote when the request failed. Then switch to Network and click Export again. (Network only records while it's open.) A new row appears for export with status 500. Click it and look at the Headers section, under Response Headers.

Copy as cURL

Right-click any request in the Network tab and choose Copy → Copy as cURL. You get a terminal command that makes exactly the same request again, headers and all. Support engineers use this constantly to reproduce a customer's problem outside the browser. It's where Lesson 5 picks up.

When you ask a customer for this

A HAR file (Network → right-click → "Save all as HAR") or a copied cURL can contain the customer's login cookies or API keys. Treat them like passwords: ask for them through your ticketing system, never a public channel, and never paste them into a shared doc.

Recap

  • HTML is the content and structure, CSS is the look, JavaScript is the behavior. The browser turns HTML into the DOM tree.
  • Elements have tags and attributes. class (many, space-separated) and id (one) are how CSS and JavaScript find them.
  • A CSS rule is a selector plus property: value; pairs. More specific selectors win; crossed-out rules in DevTools lost.
  • Margin, border, padding, content: the box model. display: none hides an element completely.
  • DevTools: Elements for what's on the page and why it looks that way, Console for errors, Network for what the page asked the server and what came back.
Interview prep

"A customer says a button is missing. How do you investigate?" A strong answer: reproduce it if I can; inspect the element to see if it's in the DOM at all, and if it is, check computed styles for display: none or zero size; check the Console for errors that stopped the page from rendering it; check Network for a failed request that the button depends on. Then compare with an account where it works.
