Talking to an API

The page in Lesson 4 got its invoices by asking a server. So do Zapier, accounting tools and every customer's own scripts. When those break, the ticket lands with you. This lesson teaches the language they speak.

New ticket · integrations · high

From lin@sprouttutoring.ca

Your API keeps rejecting my key with a 403. I've copied it exactly from the settings page three times. Is the API down?

By section 6 you'll know what a 403 means, why Lin is getting one, and how to prove it in one command.

1. A request and a response

An API (application programming interface) is a way for one program to ask another for something. On the web, they talk over HTTP, the same protocol your browser uses to load pages. Every conversation is one request and one response:

REQUEST  (you → server)                    RESPONSE  (server → you)
─────────────────────────                  ──────────────────────────
GET /api/v1/me                ← method,    HTTP/1.1 200 OK             ← status
Host: localhost:4747            path       Content-Type: application/json
Authorization: Bearer pk_…    ← headers    X-Request-Id: req_7q2…       ← headers

(no body for a GET)           ← body       { "account": { … } }         ← body
  • The method says what you want to do: GET to read, POST to create, and a few others.
  • The path says what you're talking about: /api/v1/invoices.
  • Headers are labeled extra details: who you are, what format you're sending.
  • The body is the content itself, usually JSON.
  • The status code is the server's one-number summary of how it went.

2. Anatomy of a URL

http://localhost:4747/api/v1/invoices?status=overdue&limit=3
└─┬─┘  └───┬───┘ └┬─┘└───────┬──────┘ └──────────┬──────────┘
scheme    host   port      path            query string

The query string starts at ? and holds name=value pairs separated by &. APIs use it for options like filters and page sizes. Your local Paperkite API lives at localhost:4747, which means "this computer, port 4747."

The box below sends a real HTTP request to your local Paperkite API and shows you the raw response. Under the inputs it shows the same request written as a curl command, which is how you'd send it from a terminal.

Now do the same thing in Terminal, because in a support job that's where you'll do it. Open Terminal and run:

curl -i http://localhost:4747/api/v1/health

curl sends a request and prints the response. -i means "include the response headers," which you almost always want when debugging. The flags you'll use most:

FlagMeans
-ishow the status line and headers, not just the body
-H 'Name: value'add a header (repeat for more)
-X POSTuse a method other than GET
-d '{"a": 1}'send a body (and switch to POST automatically)
-ssilent: hide the progress meter

Big JSON responses are easier to read through jq, which is installed on your Mac: curl -s http://localhost:4747/api/v1/health | jq. The | sends one command's output into the next.

4. Status codes: whose problem is it?

The first digit of a status code tells you more than anything else in the response:

ClassMeansSupport translation
2xxSuccessIt worked. If the customer is still unhappy, the problem is in what they did with the answer.
3xxRedirect, go elsewhereUsually handled automatically. Matters when a URL has moved.
4xxThe request was wrongSomething about what they sent: the key, the data, the URL. Usually fixable on their side, and the response body says what.
5xxThe server failedOur problem. Nothing the customer changes will fix it reliably. Collect the details and escalate.

The specific ones you'll meet again and again, every one of which this API can return:

CodeNameUsually means
200OKWorked; here's your data.
201CreatedWorked; a new thing was created.
400Bad RequestThe request is malformed: broken JSON, a bad parameter.
401UnauthorizedWe don't know who you are: no key, wrong key, revoked key.
403ForbiddenWe know who you are, and you're not allowed to do this.
404Not FoundThat path or that record doesn't exist (for you).
405Method Not AllowedRight path, wrong method (a POST where only GET works).
415Unsupported Media TypeThe body isn't in the format the server expects; usually a missing Content-Type.
422UnprocessableWell-formed, but the values are invalid. The body lists which fields.
429Too Many RequestsRate limited. Slow down; Retry-After says for how long.
500Internal Server ErrorA bug on the server.
502, 503, 504Bad Gateway, Unavailable, TimeoutSomething between them and the code is down or slow. Often temporary.
On the job

The 401 versus 403 distinction comes up constantly. 401: "Who are you?" The key is missing, mistyped, or revoked. 403: "I know who you are, and no." The key is fine; it just isn't allowed to do this. Lin's ticket says 403, so her key is being recognized. Copying it again won't help.

5. JSON: the format of almost every API

API bodies are almost always JSON (JavaScript Object Notation), a text format for structured data:

{
  "account": {                        ← an object: named values in { }
    "id": 1,                          ← a number
    "name": "Harbor & Pine Bakery",   ← a string, always "double quotes"
    "plan": "pro"
  },
  "api_key": {
    "scopes": ["invoices:read"],      ← an array: a list in [ ]
    "revoked": false                  ← true / false
  },
  "paid_at": null                     ← null, the same idea as in SQL
}

Objects nest inside objects, and arrays hold lists of anything. When people describe a value inside, they write a path: account.name is "Harbor & Pine Bakery"; api_key.scopes[0] is the first item in the scopes list.

JSON is strict. The three mistakes behind most "invalid JSON" errors: single quotes instead of double ('pro'), a comma after the last item ([1, 2,]), and names without quotes ({plan: "pro"}).

6. Authentication: API keys

Paperkite knows who's calling from an API key, sent in the Authorization header as Bearer followed by the key. Harbor & Pine has four keys. You can see them with SQL:

Real keys are secrets

These are practice keys on your own machine. Real API keys are passwords: anyone who has one can act as that customer. Never ask a customer to paste a key into a ticket or chat, and if they do, tell them to revoke it and make a new one. Production databases usually store only a hashed version, so support staff can't see full keys at all. You'll notice Paperkite's logs record a key's label, never the key itself.

The 403 is because API access is part of the Pro plan, and Sprout Tutoring is on Starter. If you upgrade under Settings → Billing, the same key will start working right away."

A key can also be valid but limited to certain actions, called scopes. Harbor & Pine's reporting key only has invoices:read. Try creating an invoice with it (switch the method to POST) and you'll get a different 403, with a message naming the missing scope.

7. Query strings and pages

GET /api/v1/invoices lists invoices. It accepts three query parameters: status (draft, sent, overdue, paid, void), limit (1 to 100, default 10) and page. Lists come back one page at a time, with has_more telling you whether there's another.

On the job

"Your API is missing invoices" is very often a customer who only read the first page. Their script got 10, saw has_more: true, and stopped. Ask what parameters they're sending before you look for a bug.

8. Sending data: POST, Content-Type, and validation

To create something, you POST a JSON body. Two headers matter: the Authorization header, as always, and Content-Type: application/json, which tells the server how to read the body. Forget the second one and you'll get a 415. (curl's -d labels the body as form data unless you say otherwise, so this is one of the most common curl mistakes.)

Quote the API's own words: amount_cents must be a whole number of cents (1250, not the string "1250.00"), and due_at is required, written YYYY-MM-DD. A 422 with a fields list is the API telling you exactly what to fix, so the fastest support reply forwards that list.

9. Rate limits

APIs limit how many requests a key can make per minute, so one runaway script can't slow things down for everyone. Over the limit, you get 429 Too Many Requests and a Retry-After header with the number of seconds to wait. Harbor & Pine's "Wall dashboard" key allows only 3 requests a minute.

The right fix for a customer hitting 429s is almost never "raise my limit." It's "wait Retry-After seconds before retrying," and "don't poll every second for data that changes once an hour."

10. Request IDs: the thread back to the logs

Every response from Paperkite carries an X-Request-Id header. The same id is written into the server's log line for that request. Asking a customer for the request id (or the exact time and endpoint) turns "it failed sometime yesterday" into one exact line in the logs. Many APIs (Stripe, GitHub, Twilio) work the same way.

Webhooks: an API in reverse

Sometimes the product calls the customer's server instead: "invoice paid" gets sent to a URL the customer chose. That's a webhook. The same ideas apply in reverse: if their server answers with a 4xx or 5xx, or takes too long, the delivery fails and is usually retried. "Webhook not firing" tickets are mostly the customer's endpoint returning errors, which the product's delivery log will show.

Recap

  • A request is a method, a URL, headers and maybe a body. A response is a status code, headers and a body.
  • 2xx worked, 4xx means the request was wrong (read the body for why), 5xx means the server failed.
  • 401 is "who are you?"; 403 is "I know you, and no."
  • JSON uses double quotes, no trailing commas, and has objects {}, arrays [], strings, numbers, true/false and null.
  • POSTing JSON needs Content-Type: application/json. 422 lists the fields to fix.
  • Lists come in pages; check has_more. 429 means wait Retry-After seconds.
  • curl -i reproduces anything. A request id ties a response to its log line.
Interview prep

"A customer gets a 401 from our API. Walk me through it." Ask how they send the key (the exact header, without the key itself); check it isn't revoked or from a different environment (test versus live keys); reproduce with curl -i using a key you control; check the logs by time or request id. Then explain the difference between 401 and 403 without being asked. That's the answer they want.
