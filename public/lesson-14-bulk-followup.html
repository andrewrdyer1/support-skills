1. The help desk API

Paperkite's support team works tickets through its own help desk, and like Zendesk or Intercom, it has an API. Its token is hd_test_support_team, and these editors have it in the HELPDESK_TOKEN environment variable.

RequestDoes

Changes are kept in memory by the course server, so restarting it, or the Reset button at the end of this lesson, puts every ticket back.

2. Five rules for scripts that change data

RuleWhyHow this script does it
Dry run firstYou see exactly which records it will touch before it touches any.--dry-run prints "would reply…" for each ticket and changes nothing.
Ask before actingA typo in a search term shouldn't email 400 customers.It says how many tickets it will change and waits for you to type yes. --yes skips the question when you're sure, such as in a scheduled job.
Safe to run twice (idempotent)Scripts get re-run after a crash, or by a colleague who didn't know you'd run it. Customers must not get the same reply twice.The tag marks a ticket as done. Tagged tickets are skipped.
Keep going on failureOne bad record shouldn't leave the rest half-done with no record of which.Each ticket is in its own try. Failures are collected and listed at the end, and the exit code is 1.
Say what happenedYou'll be asked "did it go out to Wren Consulting?"One log line per ticket, then a summary: updated, skipped, failed.
Why reply before tagging, and not the other way round?

Think about each step failing halfway. If the script tags first and then the reply fails, the ticket looks done: every future run skips it, and that customer never hears from you. If it replies first and the tag fails, a re-run might reply again. That's annoying, but you'd see it, and the customer still got the update.

Replying first fails more visibly and more safely, and the failure list tells you exactly which ticket to check by hand. There's rarely a perfect order. The skill is thinking through what each failure leaves behind and picking the one you can live with.

4. Testing a script that changes data

You can't test this script by running it for real over and over: every run would post more replies. So the test file has FakeHelpdesk, an in-memory help desk with the same three methods as the real client (search, add_comment, update). Every function in the script takes the client as a parameter, so tests pass the fake in and then inspect it: which tickets got a comment, which got the tag.

def test_running_twice_does_not_reply_twice():
    desk = sample()
    follow_up(desk, find_tickets(desk, ["export", "download"], "open,pending"), TAG, log=quiet)
    second = follow_up(desk, find_tickets(desk, ["export", "download"], "open,pending"), TAG, log=quiet)
    assert second["done"] == []
    assert second["skipped"] == [1, 2, 3, 4]
    assert all(len(desk.comments[tid]) == 1 for tid in [1, 2, 3, 4])

Every safety rule above has a test like this: dry run changes nothing, canceling changes nothing, running twice replies once, one failure doesn't stop the rest. When they pass, you can run the real thing with confidence. That's the point of tests: confidence before you do something you can't undo.

Help with follow_up 
for ticket in tickets:
    tid = ticket["id"]
    if tag in ticket["tags"]:
        log(f"#{tid}: already tagged {tag}, skipping")
        result["skipped"].append(tid)
        continue
    if dry_run:
        log(f"#{tid}: would reply, tag {tag}, set {new_status}")
        result["done"].append(tid)
        continue
    try:
        client.add_comment(tid, reply_for(ticket))
        client.update(tid, status=new_status, add_tags=[tag])
        log(f"#{tid}: replied, tagged {tag}, set {new_status}")
        result["done"].append(tid)
    except HelpdeskError as e:
        log(f"#{tid}: FAILED: {e}")
        result["failed"].append((tid, str(e)))

log is a parameter that defaults to print. Tests pass a function that collects lines instead, so they can check what was logged.

Help with the confirmation step 
if todo and not args.dry_run and not args.yes:

    if answer.strip().lower() != "yes":

confirm defaults to Python's input, which waits for you to type. Tests pass lambda prompt: "no" instead. Same trick as the fake sleep in Lesson 13.

Recap

  • Scripts that change data: dry run, confirm, idempotent, keep going on failure, report everything.
  • Think through what each step failing halfway leaves behind, and order the steps for the failure you can live with.
  • argparse for options (action="store_true" for flags, type=int for numbers, choices=[…] to limit values).
  • Wrap the API in a small client class. Pass the client in, so tests can use a fake.
  • Exit codes: 0 for success, non-zero when something failed, so other tools (and schedulers) can tell.
