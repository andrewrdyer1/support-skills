Lesson 15 · four script cases · about 2 hours, at your own pace

Script cases

Four real support tasks. Each has a short spec, a test suite, and an empty starter. No step-by-step this time: read the spec, read the tests, plan, build, run. This is what a take-home exercise for a support engineering job looks like.

How to work a case
  1. Read the spec at the top of the starter file. It's the "ticket."
  2. Read the tests. They're the precise version of the spec: exact outputs, edge cases, what counts as done.
  3. Plan in comments before writing code: one line per step.
  4. Build one function at a time, running just its tests (-k name).
  5. Run the real script and read the output like the person who asked for it would.

All four live in workspace/lesson15/. Run every case's tests with python -m pytest lesson15, or one case with python -m pytest lesson15/test_sla_alert.py. Finished versions are in course/solutions/lesson15/.

Warm up: SQL from Python

Two of the cases query the database directly with psycopg, the standard Postgres library. The pattern is always the same:

import psycopg

with psycopg.connect("postgresql://learner@localhost:5488/paperkite") as conn:
    with conn.cursor() as cur:
        cur.execute("select id, name from accounts where status = %s", ("past_due",))
        rows = cur.fetchall()        # a list of tuples: [(153, "Sable Dental"), ...]
Never build SQL with f-strings

cur.execute(f"... where name = '{name}'") works until a customer's name contains a quote, and then it's either an error or, if the text came from a user, a SQL injection hole: whoever controls the text controls the query. Always put %s in the SQL and pass the values separately. psycopg sends them apart from the query, so they can never be run as SQL.

Values come back as Python types: timestamptz columns are datetime objects (with a timezone), date columns are date objects, and null is None.

Case A: invites nobody accepted

From the CX operations lead

Sam's invite typo made me wonder how many more there are. Can you get me everyone who was invited more than a week ago and still hasn't logged in, on accounts that are active or in trial? Flag the likely typos. We'll reach out to the account owners.

File: lesson15/stuck_invites.py · Tests: test_stuck_invites.py · Uses: SQL from Lessons 1 and 2, psycopg, dates, CSV.

Done when: all 7 tests pass, and the script prints 47 stuck invites with one possible typo (Sam's) and writes out/stuck_invites.csv.

Hint 1: the query

You need the user, their account, and the account's owner, so join users twice: once as the invited user (u) and once as the owner (o, with o.role = 'owner' in the join condition). Then filter: not an owner, never logged in, created on or before the cutoff, account active or trialing.

Hint 2: the cutoff and the date

from datetime import timedelta; the cutoff is today - timedelta(days=7), passed as the %s. The created_at you get back is a datetime; created_at.date().isoformat() gives "2026-10-20".

Hint 3: looks_like_typo

Compare the lowercase part after the @: email.split("@")[-1].lower(). Priya's mixed-case address must not count as a typo.

Case B: revoked keys still knocking

From the integrations team

When a customer revokes a key but forgets to update the integration using it, the integration fails quietly forever. Can we find the ones still trying? Those customers probably have a broken sync and don't know.

File: lesson15/revoked_keys.py · Uses: log parsing from Lesson 12, psycopg, dicts keyed by tuples.

The wrinkle: logs record a key's label, never the key itself, and labels aren't unique. Account 39 has two keys called "Accounting sync": one revoked, one active. You can't tell from the log which one made each request, so the report notes it. That note is exactly the kind of detail that makes a support report trustworthy.

Done when: 4 tests pass and the script lists 5 revoked keys still in use, led by account 39 and account 189 with 14 attempts each, account 39 carrying the note.

Hint 1: shape of the data

Build a dict keyed by (account_id, label) from the api_keys table. dict.setdefault(key, {...}) gets the existing value or inserts a default, which is handy when several keys share a label.

Hint 2: counting and the latest time

Log times are ISO strings, which compare correctly as text, so max(row["last_attempt"], e["time"]) keeps the latest. Sort with key=lambda r: (-r["attempts"], r["account_id"]): the minus sign sorts attempts biggest first, and account_id breaks ties.

Case C: clean a messy import

From an onboarding specialist

Copper Studio sent their team list to bulk-import (data/contacts_import.csv). It's a mess: capitals, spaces, duplicates, some emails that aren't emails. Can you give me a clean file to import and a list of what you rejected and why, so I can send it back to them?

File: lesson15/clean_import.py · Uses: CSV, string cleaning from Lesson 11, a regular expression, sets.

Open the CSV first (open data/contacts_import.csv) and look at it. The rules are in the spec at the top of the file.

Regular expressions describe text patterns. You need one, for "plausible email":

import re
EMAIL = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")
EMAIL.match("ruth.ueda@copperstudio.com")   # a match object (truthy)
EMAIL.match("pat.doyle@copperstudio")       # None

Read it as: from the start (^), one or more characters that aren't @ or whitespace, then @, then more of those, a literal dot (\.), more of those, and the end ($). It's not perfect email validation (nothing short is), but it catches every real mistake in this file.

Done when: 5 tests pass, and the script reports 58 rows: 46 ready to import, 12 rejected, each with its line number in the original file.

Hint: duplicates and line numbers

Keep a set of emails you've accepted; if a cleaned email is already in it, reject the row as "duplicate". for line, row in enumerate(rows, start=2): numbers the rows from 2, because line 1 is the header. Reject rows with their original values, so the customer recognizes them.

Case D: response-time alert

From the support lead

Two urgent tickets sat unanswered over a weekend last month. I want a script we can run every half hour that posts in Slack if any urgent or high ticket has gone past its target with no reply at all.

File: lesson15/sla_alert.py · Uses: the help desk API, datetimes and timezones, exit codes.

Timezones: the API sends times like 2026-10-29T13:21:13.325Z. The Z means UTC. datetime.fromisoformat(text.replace("Z", "+00:00")) turns that into a timezone-aware datetime. Subtracting two datetimes gives a timedelta; .total_seconds() / 3600 is hours. Always compare times that both carry a timezone, or Python will refuse.

Exit codes are how scripts talk to schedulers: 0 means "all fine," anything else means "do something." A scheduler (cron, GitHub Actions, a monitoring tool) can post to Slack only when the exit code is 1. That's why main returns 1 when there are breaches.

Done when: 4 tests pass, and the script prints an alert for 2 tickets (#592 and #864, both high priority, waiting over a day) and exits with code 1. Check the exit code with echo $? right after running it.

Hint: which tickets count

Priority must be in TARGET_HOURS (urgent or high), first_response_at must be empty, and the hours waited must be strictly greater than the target. Exactly 4 hours for a high ticket is not yet a breach. The test checks that edge.

After the cases

You've now written the four kinds of script support teams lean on most: a report from the database, a report from logs, a data cleanup, and an alert. With Lesson 14's bulk update, that's five. For interviews:

  • Put them on GitHub. A repo with these scripts, their tests, and a README explaining what each solves is a better answer to "do you have scripting experience?" than any course certificate. (Remove anything you didn't write, like the course's own files, and keep the data made-up.)
  • Be ready to explain one end to end: what it was for, why it's safe to run, how you tested it, and what you'd improve.
  • Mention the judgment calls: the ambiguous labels in Case B, the reply-then-tag order in Lesson 14, the "exactly 4 hours" edge in Case D. Interviewers remember candidates who noticed the edges.
