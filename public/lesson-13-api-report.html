Script: an API report

Lesson 5 made API calls one at a time. Scripts make hundreds, and some of them fail. This lesson builds a report the way production scripts are built: every page fetched, temporary failures retried, permanent ones explained, and secrets kept out of the code.

From the customer success team

Harbor & Pine asked if we can send them a list of their overdue invoices with how late each one is, so they can chase clients before month end. Can you script it? Other customers will want the same thing.

1. Warm up: requests

requests is the Python library for HTTP, and it's what nearly every support automation script uses. A request is one function call: requests.get(url, headers=…, params=…). The response has .status_code, .headers, .ok (True below 400) and .json().

Keys come from the environment, not the code. os.environ is a dict of environment variables, settings your terminal passes to every program it runs. Keeping the key there means the script can be shared, committed to git, or pasted into a ticket without leaking anything. These editors have PAPERKITE_API_KEY set to Harbor & Pine's reporting key.

2. What a real script has to handle

Those three work when everything goes right. A script that runs every week for every customer needs to handle what goes wrong:

SituationWhat the script should do
More results than one pageKeep asking for the next page while has_more is true.
429 rate limitedWait Retry-After seconds, then try again.
5xx server errorOften temporary. Wait a little longer each time (2s, 4s…) and retry a few times. This is called exponential backoff.
Any other 4xxDon't retry: the request itself is wrong. Stop and show the API's message.
Server unreachableSay so in plain words, not a 40-line traceback.
No API key setSay how to set it.

Exceptions you define yourself

When a function can't do its job, it can raise an exception, and whoever called it decides what to do. The script defines its own:

class ApiError(Exception):
    """The API refused the request in a way that retrying won't fix."""

Then request_with_retry raises ApiError("403 from GET …: The starter plan does not include API access."), and main catches it with except ApiError as e: and prints a clean message. Low-level code reports problems; top-level code decides how to show them.

Testing code that talks to a server

How do you test "waits 7 seconds after a 429, then succeeds" without waiting 7 seconds or making the server misbehave? You give the function a fake. Open test_overdue_report.py and look at FakeSession: it has the same .request(…) method as a real requests Session, but returns responses the test chose, and records what was asked. And request_with_retry takes sleep as a parameter, so the test passes a FakeSleep that writes down how long it was asked to wait instead of waiting.

def test_waits_retry_after_on_429_then_succeeds():
    session = FakeSession([FakeResponse(429, headers={"Retry-After": "7"}), FakeResponse(200)])
    sleep = FakeSleep()
    response = request_with_retry(session, "GET", "http://x/api", sleep=sleep)
    assert response.status_code == 200
    assert sleep.waits == [7]

This is the most useful testing idea there is: pass in the things your code depends on (the session, the clock, the sleep) instead of reaching for them directly, and tests can swap in fakes. The test file also has a few live tests marked @live that call your real local API, and skip themselves if the server isn't running.

Help with request_with_retry 
for attempt in range(1, max_tries + 1):
    response = session.request(method, url, params=params, json=json, timeout=10)
    if response.status_code < 400:
        return response
    if response.status_code in RETRY_STATUSES and attempt < max_tries:
        sleep(float(response.headers.get("Retry-After", 2 ** attempt)))
        continue
    raise ApiError(f"{response.status_code} from {method} {url}: {error_message(response)}")

range(1, max_tries + 1) counts 1, 2, 3. continue jumps to the next loop. 2 ** attempt is 2 to the power of attempt. timeout=10 means "give up if the server doesn't answer in 10 seconds", and every real request should have one, or a hung server hangs your script forever.

Help with fetch_all 
items = []
page = 1
while True:
    query = {**(params or {}), "limit": page_size, "page": page}
    body = request_with_retry(session, "GET", API + path, params=query, sleep=sleep).json()
    items.extend(body["data"])
    if not body["has_more"]:
        return items
    page += 1

{**a, "x": 1} makes a new dict with everything from a plus x. params or {} uses an empty dict when params is None. .extend adds every item from one list onto another.

Recap

  • requests.get(url, headers=…, params=…, timeout=…); check .status_code, read .json().
  • Secrets live in environment variables: os.environ.get("PAPERKITE_API_KEY") in code, export in Terminal.
  • Follow has_more for every page. Retry 429 and 5xx with waits; never retry other 4xx.
  • Define your own exception, raise it low, catch it high, and print a human sentence.
  • Pass dependencies in (session, sleep, today) so tests can use fakes. Live tests prove the real thing works.
