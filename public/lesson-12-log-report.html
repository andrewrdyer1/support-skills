Script: a log triage report

In Lesson 6 you searched logs by hand. Now you'll write the script that does the first pass for you: what's failing, where, and for whom. Along the way you'll set up a real project workflow: an editor, a terminal, and tests that tell you when you're done.

Slack · #support-leads

Every Monday someone eyeballs the API logs for anything weird and it takes half an hour. Could we get a script that prints the failures by endpoint and which accounts are hitting 500s, and saves a CSV we can paste into the weekly doc?

1. Warm up: files, JSON lines and CSV

Three short exercises with the tools the script needs. They run in workspace/, so data/history.log is the same log file you searched in Lesson 6.

Reading a file. with open(path) as f: opens a file and closes it automatically when the indented block ends. Looping over f gives you one line at a time, which works even for a log file bigger than your computer's memory.

JSON lines. Each log line is its own JSON object, so json.loads(line) turns each into a dict. A Counter is a dict that starts every count at zero, which saves you the .get(x, 0) dance.

CSV. csv.DictReader reads a CSV file and gives you each row as a dict keyed by the header row. Every value is text, so convert numbers yourself.

Open Terminal in the workspace folder with the course's Python turned on:

Now run the tests:

You'll see a wall of Fs and red. That's the starting point. Read the summary at the bottom:

FAILED lesson12/test_log_report.py::test_parse_line_reads_json - assert None == {…}
…
8 failed, 3 passed in 0.03s

Three pass already: two check that bad lines give None (which an empty function returns anyway), and normalize_path is written for you as an example. Each FAILED line names a test, and the bit after the dash is why. That's your to-do list.

3. How tests work

Open test_log_report.py and read the first test:

def test_parse_line_reads_json():
    entry = parse_line('{"status": 500, "path": "/api/v1/me"}\n')
    assert entry == {"status": 500, "path": "/api/v1/me"}

That's all a test is: a function whose name starts with test_ that calls your code and asserts something about the result. If the assert is false, the test fails and pytest shows both values. pytest finds every test_*.py file and every test_* function in it automatically.

Commands you'll use constantly:

CommandDoes
python -m pytest lesson12run every test in the folder
python -m pytest lesson12 -k parse_lineonly tests whose name contains "parse_line"
python -m pytest lesson12 -xstop at the first failure (less to read)
python -m pytest lesson12 -vone line per test, by name

The workflow, which is how most professional code gets written: run the tests, pick one failing test, make it pass, run them again. Small steps. You always know where you are.

4. Build it, one function at a time

Work top to bottom in log_report.py. Each function has a docstring saying what it should do and TODO comments with a nudge. Notes for each, if you need them:

parse_line

Three steps: line = line.strip(); if it's empty, return None; then try: return json.loads(line) with except json.JSONDecodeError: return None. That except is the difference between a report and a crash when one log line was cut off halfway, which really happens.

Check: python -m pytest lesson12 -k parse_line

read_requests

Same shape as the first warm-up: with open(path) as f:, for line in f:, entry = parse_line(line), then append it if entry is not None and "status" in entry. Notice how it reuses parse_line: small functions that each do one thing are easy to test and easy to combine.

failures_by_endpoint

A Counter can count pairs. Build one from a generator expression (a comprehension in round brackets):

counts = Counter(
    (normalize_path(e["path"]), e["status"]) for e in entries if e["status"] >= 400
)

counts.most_common() gives [((path, status), count), …], biggest first. The test wants flat tuples, so unpack each one: [(path, status, count) for (path, status), count in counts.most_common()].

top_accounts

One Counter of e["account_id"] for entries whose status equals the one asked for, then return counts.most_common(n).

write_csv 
with open(path, "w", newline="") as f:
    writer = csv.writer(f)
    writer.writerow(header)
    writer.writerows(rows)

"w" opens for writing (replacing the file). newline="" stops blank lines appearing between rows on some systems; the csv docs ask for it.

When python -m pytest lesson12 says 11 passed, run the real thing:

python lesson12/log_report.py data/history.log

You'll get the failures table and the top accounts for 500s, and a file at workspace/out/failures.csv. Open it with open out/failures.csv and it lands in Numbers or Excel, ready for the weekly doc.

5. Write your own tests

At the bottom of the top_accounts section of the test file is a comment asking for two more tests. Write them:

  1. One that checks top_accounts(entries, 500, n=3) returns exactly 3 items.
  2. One that checks a status nobody got (418) returns an empty list.

Then prove they're really testing something: break top_accounts on purpose (change most_common(n) to most_common()), run the tests, and watch yours fail. Put it back. A test you've never seen fail might not be testing anything.

One way to write them 
def test_top_accounts_respects_n():
    assert len(top_accounts(read_requests(LOG), 500, n=3)) == 3


def test_top_accounts_unknown_status_is_empty():
    assert top_accounts(read_requests(LOG), 418) == []

Good test names say what they promise, so a failure reads like a sentence: "top accounts respects n" failed.

Recap

  • with open(path) as f: for line in f: reads any size of file safely.
  • json.loads for JSON lines; csv.DictReader / csv.writer for CSV.
  • Counter counts anything, including pairs, and .most_common(n) sorts for you.
  • Small functions that do one thing, combined in main.
  • Tests are functions named test_… that assert. Red, make one pass, green, repeat. Watch a new test fail once.
