Functions and errors

Every script you'll meet at work is built from small functions, and every script you write will crash a few times on the way. This lesson takes functions one idea at a time, with an example and a walkthrough before each exercise, then shows you how to read the error Python gives you when something breaks.

1. Why functions

A function is a named piece of code that does one job. You've been using other people's all along: print(), len(), round(). Now you write your own.

Here's why it's worth it. Picture a 60-line script that reads an export, works out who owes money, and prints a summary. Written top to bottom, it's hard to follow and hard to fix. Written as five functions, called read_invoices, unpaid, total, format_money and main, you can read the names and know what it does, fix one piece without touching the others, and test each piece on its own. Lesson 12's tests do exactly that.

What Python does on the first print line, step by step:

  1. It sees ticket_label(1152, "CSV export broken") and jumps into the function.
  2. Inside, ticket_id is 1152 and subject is "CSV export broken", for this call only.
  3. The body runs. return sends back "#1152: CSV export broken" and leaves the function.
  4. Back on the calling line, the call is replaced by that answer, so the line is now print("#1152: CSV export broken"), which runs.

The second call does the same with new values. The function doesn't remember anything from the first call.

Order in the file

Python reads a file top to bottom, so a function has to be defined above the line that calls it. That's why scripts put their functions first and the calls at the bottom. Call one before its def and you get NameError: name 'ticket_label' is not defined.

People mix the words up all the time and nobody minds. What matters is how they match up: by position. The first argument goes into the first parameter, the second into the second. Swap them and Python won't complain; you just get the wrong answer:

What a function can see

Variables made inside a function disappear when it returns. If a function sets total = 0 and adds to it, there is no total outside afterwards. Use return total and store the answer: t = add_up(amounts). Going the other way, a function can read variables defined at the top of the file, like a PRICES dict, but pass in what it needs as parameters wherever you can. That's what lets a test call it with different data.

4. return versus print

This is the mistake almost everyone makes at the start, because both seem to "give you the answer" when you run the code.

print(x)return x
What it doesshows x on the screenhands x back to the line that called the function
Can the caller use the value?No. The call gives back None.Yes: store it, compare it, add it up, print it
Does the function keep going?yesno, return ends it right there
Who should use itthe part of a script that shows the final resultevery function that works something out

None is what a function gives back when it never reaches a return. So when a value is unexpectedly None, the first thing to check is the function it came from: does every path through it end in a return?

A print inside a function is fine while you're working out what's going on. Just make sure the answer leaves through return.

7. Defaults and named arguments

A parameter can have a default, written name=value in the def line. If the caller leaves that argument out, the default is used. Parameters with defaults go after the ones without.

Naming arguments in a call is optional, but it makes calls like export(path, True, False) readable: export(path, dry_run=True, notify=False) says what each value is for.

The next exercise formats money. A reminder from Lesson 7: format codes like :,.2f only work inside an f-string's curly brackets, so work out the number, then format it inside the f-string: f"{symbol}{cents / 100:,.2f}". Written anywhere else, :,.2f is a SyntaxError.

8. A one-line if

When a function picks between two values, there's a short form called a conditional expression. The order is: the value if true, if the condition, else the value if false.

It's the same idea as SQL's case when hours_waiting > 24 then 'urgent' else 'normal' end. The else is required, since the expression always has to produce a value. Keep it for short choices between two values; anything longer reads better as a normal if/else block.

10. Functions and methods

You've seen two ways of calling things: len(statuses) and email.lower(). The second kind, with a dot, is a method: a function that belongs to one type of value. They're the same thing underneath:

Built-in functionsMethods
Writtenlen(x)x.lower()
Forgeneral jobs that work on many typesactions that belong to one type
Exampleslen, sum, min, max, sorted, print, type, int, str, float, roundtext: .strip(), .split(), .replace()
lists: .append(), .count()
dicts: .get(), .items()

Why len(x) and not x.len()? Python's designers chose to make "how many" one function that works on text, lists and dicts alike. Other languages chose differently (JavaScript has x.length). There's no rule to work out; after a week of writing scripts the common ones stick. Guess wrong and Python says so: AttributeError: 'list' object has no attribute 'len'.

The functions you write with def are the first kind, called by name. Writing your own methods means defining your own type (a "class"), which support scripts rarely need.

sorted(statuses) and statuses.sort() both sort. What's the difference?

sorted() is a built-in function: it works on any collection and gives you back a new sorted list, leaving the original alone. .sort() is a list method: it rearranges that list itself and returns None. So x = statuses.sort() leaves x as None, a classic bug.

11. When it breaks: reading a traceback

When Python hits an error it can't handle, it stops and prints a traceback: the chain of function calls that led to the error, oldest first. Functions are why it's a chain: main called summarize, which failed. Read it from the bottom up:

Traceback (most recent call last):
  File "/Users/you/workspace/report.py", line 31, in <module>
    main()
  File "/Users/you/workspace/report.py", line 26, in main
    print(summarize(rows))
  File "/Users/you/workspace/report.py", line 14, in summarize
    total += row["amount"]
KeyError: 'amount'
  1. The last line is what went wrong: the error's type and a detail. Here, a dict had no key 'amount'.
  2. The lines just above it are where: file, line number, the function it was in, and the code on that line.
  3. Further up is how the script got there: the top level (<module>) called main, which called summarize. You usually only need this when the bottom frame is inside a library rather than your own code.
ErrorUsually means
NameError: name 'x' is not defineda typo in a name, using it before it's set, or calling a function above its def
TypeErrorthe right idea with the wrong type: text plus a number, the wrong number of arguments, doing math with None
KeyError: 'x'a dict has no such key. Check the spelling and capitals, or use .get()
IndexError: list index out of rangeasked for item 5 of a 3-item list (often: the list is empty)
AttributeError: 'NoneType' object has no attribute …a variable you expected to hold something is None. Often a function that printed instead of returning.
AttributeError: 'list' object has no attribute …that type has no such method: x.len() instead of len(x)
ValueErrorthe right type with a bad value: int("abc")
SyntaxError, IndentationErrorPython couldn't read the code at all: a missing :, bracket or quote, = where you meant ==, uneven indents. Look at the line shown and the one above it.
A SyntaxError means nothing ran

Most errors happen partway through: everything before the bad line ran, and you may see some output first. A SyntaxError is different. Python reads the whole file before running any of it, and if it can't make sense of one line, it refuses to start. So no output at all, plus a SyntaxError, means "fix the typing", not "fix the logic". The little ^ under the line points at where Python got confused, which is often just after the real mistake.

Three broken functions to fix. Run each one first and read the error before you change anything.

How to debug anything

When the traceback doesn't make it obvious: print what you have, right before the failing line. print(repr(row), type(row)) shows exactly what the value is, including stray spaces (repr puts quotes around text so you can see them). Nine times out of ten the value isn't what you assumed. Then shrink the problem: copy the one failing line into the >>> prompt with a made-up value and poke at it. Cursor and VS Code also have a debugger that pauses on a line so you can inspect everything; it's worth learning once prints stop being enough.
