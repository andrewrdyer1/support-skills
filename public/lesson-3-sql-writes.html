1. This lesson's practice database

Every editor in Lesson 1 and 2 was read-only. The ones in this lesson say practice writes, always rolled back: your statement really runs, and you see exactly what it changed, then everything is undone. Nothing you do here is saved, so the other lessons see the same data. Try deliberately doing the worst thing you can:

UPDATE 240. Every customer just canceled. No where means every row. In production that's an incident, a restore from backup, and a very long day for everyone. Here, it was rolled back before you saw it.

2. UPDATE

update table_name
set column = new_value, other_column = other_value
where which_rows
returning the_columns_you_want_to_see;
  • set lists the changes, separated by commas.
  • where works exactly like in a select. It decides which rows change. Leave it out and the answer is "all of them."
  • returning is optional and shows the changed rows, like a select of just what you touched. It's a Postgres feature (SQLite has it too; SQL Server's version is called output; MySQL has none, so there you run the select again afterwards).

When an update finishes, the database tells you how many rows it changed: UPDATE 1, UPDATE 240, UPDATE 0. That number is the most important thing on your screen. Before you run anything, you should already know what it should be.

3. The checklist

This is the whole lesson in six lines. The rest is practice.

  1. Select first. Write a select with the exact where you'll use, and look at the rows. Now you know the count to expect.
  2. Save the before. Paste that select's output into the ticket. It's your undo: if anything goes wrong, you know the old values.
  3. Open a transaction with begin, so nothing is permanent yet.
  4. Run the change, with returning, and compare the count to step 1.
  5. Commit if it matches, roll back if it doesn't. No exceptions, no "it's probably fine."
  6. Target by id whenever you can. An id matches one row forever; a name or a label might match two, or match a different row next week.

4. Transactions: BEGIN, COMMIT, ROLLBACK

A transaction is a group of statements that either all happen or none do. You start one with begin. Until you finish it, your changes are visible to you but nobody else. Then:

  • commit makes everything since begin permanent.
  • rollback throws it all away, as if you never ran it.

Here's the full checklist as one run. This editor accepts several statements, and shows the result of each one in turn:

Before, change, after, undo. Now change the last line to commit; and run it again. This practice database refuses every commit, so you get an error instead. In a real database, that's the moment the change becomes permanent.

Without BEGIN, every statement commits instantly

psql, and most database tools, run in autocommit mode: a statement typed on its own is committed the moment it finishes. There is no undo. If you forget begin, the checklist's safety net is gone. Type begin; first, every time, until it's a reflex.

In a real terminal it looks like this. The lines starting with paperkite=* are inside the transaction: psql adds the * to remind you one is open.

paperkite=> begin;
BEGIN
paperkite=*> update users set email = 'sam@harborandpine.com' where id = 4 returning id, email;
 id |         email
----+-----------------------
  4 | sam@harborandpine.com
(1 row)

UPDATE 1
paperkite=*> commit;
COMMIT
On the job

Don't leave a transaction open. While yours is open, the rows you changed are locked: the app, and the customer clicking Save, wait until you finish. Begin, check, decide, finish. Don't start one and go to lunch.

5. Updates that use the current value

The right side of set can be any expression, including the column itself: set seat_limit = seat_limit + 2. That's how you extend, add or adjust without retyping the old value.

6. The WHERE that matches too much

Forgetting the where entirely is rare, because it looks wrong. The real mistake is a where that looks right and matches more than you meant. The row count is how you catch it.

A habit that prevents this

Write the change as a select first: select * from tickets where assignee = 'Bea' and status = 'open'. When the rows look right, replace only the first line with update tickets set assignee = 'Dani'. The where you checked is the where you run.

7. INSERT

insert into table_name (column, other_column)
values (value, other_value)
returning id;

The column list and the values line up in order. Columns you leave out get their default: for an id column, that's the next number from a sequence, a counter the database keeps for the table. Leave id out and let it choose. Several rows at once are just more brackets: values (…), (…), (…).

Run the answer two or three times with Just run and watch the id go up, even though every run was rolled back. Sequences never go backwards, not even on a rollback, because two people inserting at the same moment must never get the same number. This is why real tables have gaps in their ids, and why a missing id never proves a row was deleted.

8. DELETE

delete from table_name
where which_rows
returning the_columns_you_want_to_see;

Deleting is the change you can't take back once committed, so most apps avoid it. Instead of deleting a key, Paperkite sets revoked_at; instead of deleting an account, it sets status = 'canceled'. That's called a soft delete, and it keeps the history. When a customer asks you to delete something, check first whether the app already has a softer way.

9. After the change

The database is right now, but you're not done. A direct write skips everything the app would have done around it. Changing Sam's address didn't send him an invite. That's why your lead said to hit Resend invite in the admin panel afterwards. Then you write two things.

Recap

  • update … set … where … returning …; insert into … (columns) values (…); delete from … where ….
  • No where means every row. A where that's too loose is the more common mistake.
  • Know the row count before you run the change. If the database says a different number, roll back.
  • begin first. commit keeps it, rollback undoes it. Without begin, there's no undo.
  • Target by id. Save the old values in the ticket. Prefer a soft delete or the app's own tool.
  • A direct write skips the app's side effects: do those by hand (resend the invite).
Interview prep

"How would you safely update a few hundred rows in production?" Your answer is the checklist: select first with the same where and note the count; save the current values; begin; run the update with returning; compare the count; commit only if it matches, otherwise roll back; then do whatever the app would have done (emails, cache) and write it up in the ticket. Mention having someone review the query first, and that you'd rather use an admin tool or the API if one exists. That answer, said calmly, is most of what they're listening for.
