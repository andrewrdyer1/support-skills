Working a real incident

Everything so far comes together here. Three customers say exports are broken. You'll reproduce it, find the exact line of code that fails, work out who else is affected, give customers a workaround, and write the ticket an engineer can fix in ten minutes.

Ticket #1152 · bug · high · assigned to you

From maya@harborandpine.com · Oct 29, 2:21 PM UTC

Hi, I'm trying to export our invoices to CSV for month end and it just says "Something went wrong. Please try again later." I've tried three times. It worked fine last month. Our accountant needs this by Monday.

Slack · #support-leads

Seeing a couple of export tickets come in. Can you own this one? I need to know what's happening, how many customers it affects, whether there's a workaround, and a ticket for engineering. Thanks.

That message is a support engineer's job description in four parts. Here's the order you'll work through them, which is the order that works on almost any incident:

  1. Gather facts. Who, what, when, exact words.
  2. Reproduce it. See it fail yourself.
  3. Find the evidence. Logs, stack trace, code.
  4. Find when it started. What changed?
  5. Size the impact. Who else, and how bad.
  6. Find a workaround. Unblock customers while engineering fixes it.
  7. Write it up. The bug ticket, and the customer replies.

1. Gather facts

Maya gave you a lot already: the feature (CSV export), the exact message, three attempts, and "it worked last month," which is a hint that something changed. The events table records each export attempt. Get the precise times:

Three attempts on Oct 29, each one failing a fraction of a second after it started. Now, is it only Harbor & Pine? Search the tickets:

Three customers in two days. Different words for the same thing, which is why you searched for both "export" and "download." Customers never use the same words you would.

3. Find the evidence: logs and the stack trace

Paste your request id into the search box. (Or search export and set the level to error to see every failure, including the customers'.)

Expand your line. Each log line is one JSON object, and each field answers a question:

FieldAnswers
timeWhen, in UTC (the Z at the end means UTC)
levelHow serious: info is normal, warn is a client error, error is the server failing
request_idWhich exact request; matches the X-Request-Id header
method, path, status, msWhat was asked, what came back, how long it took
account_id, user_idWho
error.messageWhat went wrong, in the code's words
error.stackWhere in the code it went wrong

Reading a stack trace

Here's the stack from that log line, a little tidied:

TypeError: Cannot read properties of null (reading 'toISOString')
    at invoiceRow        (src/exports.mjs:23:25)
    at exportInvoicesCsv (src/exports.mjs:41:16)
    at exportInvoices    (src/api.mjs:198:30)
    at async serveApi    (server.mjs:47:14)
    …

(In the log it shows full paths starting file:///Users/…. The customers' failures from before today show only the first two lines.)

  • The first line is the error itself. Read it word by word: something tried to read toISOString from a value that was null. Null has no properties, so the code crashed. This is the single most common error in JavaScript.
  • Each at line is a function that was running, innermost first. Read upward from the bottom and it's the story of the request: the server's serveApi ran exportInvoices, which called exportInvoicesCsv, which called invoiceRow, where it broke. (async just marks a function that was waiting on something, here the database.)
  • file:line:column says exactly where. exports.mjs:23:25 is line 23, column 25.

Read the top frame first. That's where it broke. The frames below are how the code got there.

Read the code

You don't need to be able to write this code. You need to read it well enough to say what's wrong. Line 23 is highlighted:

Lines 21 to 24 in plain English: if the invoice's status is "paid" or "void", the "Paid on" value is the date from paid_at; otherwise it's blank. The ? : is a ternary, an if/else in one expression: condition ? value if true : value if false.

Now read the comment at the top of the file (lines 3 to 5). The developer assumed every void invoice had been paid first and then refunded, so it would always have a paid_at.

4. Find when it started

"It worked last month" means something changed. The fastest question in any incident is what changed, and when? Find the very first failure:

Now look at what else happened that day. Products record their deploys (releases of new code). Search the logs for deploy:

And Paperkite's changelog says the same thing in human terms:

The deploy went out at 15:02 UTC on Oct 28 and added the "Paid on" column. The first failure was 53 minutes later. No failures ever before it. That's not proof on its own (correlation isn't causation), but combined with a stack trace pointing at the exact code the deploy added, it's as close to proof as support work gets.

Confirm the theory with data

The theory: an account's export crashes if it has a void invoice with no paid_at. If that's right, Harbor & Pine must have one.

Harbor & Pine has two void invoices. Why doesn't the older one break the export?

INV-0021 was paid and then refunded, so it has a paid_at. That's the case the developer imagined. INV-0046 is a duplicate that was voided before anyone paid it, so paid_at is null. That's the case nobody thought of, and it was created on Oct 27, the day before the deploy. On Oct 28 the new code met it.

5. Size the impact

Your lead asked "how many customers?" There are two honest answers, and you should give both: who has already hit it, and who will the next time they export.

So: 10 accounts have hit it, and 38 have the data that will trigger it. Only three of the ten wrote in. That's normal. Most customers who hit a bug never tell you, which is why sizing from data beats counting tickets.

One more useful number: exports that still work since the deploy. Most do. That tells engineering it isn't "exports are down," it's "exports fail for a specific kind of data," which points straight at the cause.

Stretch: which accounts are at risk but haven't failed yet?

A subquery is a query inside another. not in (select …) removes everything the inner query returns:

select distinct a.name
from invoices i
join accounts a on a.id = i.account_id
where i.status = 'void'
  and i.paid_at is null
  and a.status <> 'canceled'
  and i.account_id not in (
    select account_id from events where name = 'export_failed'
  );

This is the list a CX team would use to warn customers before they hit it.

6. Find a workaround

The fix needs an engineer. Maya needs her export by Monday. A workaround is a way to get the customer what they need now, without the fix.

The export takes optional from and to dates (by issue date, YYYY-MM-DD). The bad invoice was issued on Oct 27. An export whose range doesn't include that day never meets it.

Is this a complete workaround for Maya? What's missing?

Nearly. Two exports cover everything: ?to=2026-10-26 and ?from=2026-10-28. Only Oct 27 is left out, and that day has two invoices: the voided duplicate (INV-0046) and the real one (INV-0045). So she'd be missing INV-0045 and would need to add it by hand.

Say that plainly in the reply. A workaround with a known gap that you tell them about is fine. One that silently drops a row from their month-end books is worse than no workaround.

Watching logs live in Terminal

Open a second Terminal window and run:

tail -f ~/Developer/support-skills/logs/app.log

tail -f prints new lines as they're written. Send a few requests from this page and watch them appear. To find things in a log file, use grep:

grep '"status":500' ~/Developer/support-skills/logs/history.log | jq

prints every failed request, formatted. On a real job the logs live in a tool like Datadog, Kibana or CloudWatch, but the searching is the same idea.

7. Write it up

A bug ticket is a handoff. The engineer who picks it up wasn't in your head for the last hour. A good one lets them start fixing without asking you a single question. The parts:

PartWhat goes in it
TitleWhat fails and under what condition. Not "export broken."
ImpactWho and how many, already and at risk. Severity, and why.
Steps to reproduceExact steps or a curl command. Expected versus actual.
EvidenceRequest ids, the error message, the top of the stack trace.
Cause (suspected)What you think is wrong, labeled as a theory, with why.
StartedWhen, and what changed then.
WorkaroundWhat customers can do now, and its gaps.
Linked ticketsThe customer tickets, so they can be updated when it's fixed.

The customer reply

Different reader, different job. Maya doesn't need the stack trace. She needs to know you've found it, what to do now, and when she'll hear back.

Reply to Maya

Hi Maya, I've found the problem, and it's on our side, not anything you did. A change we made on Oct 28 breaks the export when an account has a voided invoice that was never paid. Yours is INV-0046, the duplicate from Oct 27.

To get your month-end file now, export twice with a date range: once up to Oct 26, and once from Oct 28 onward. Those two files have everything except Oct 27, which is just INV-0045 (Westfield Realty, $1,521.99) and the voided duplicate. Our engineers have the details and I'll update you here as soon as the fix is out, before Monday if I can.

Notice what it does. The answer is in the first sentence. It takes responsibility. It names her invoice so she knows you looked. The workaround is concrete and says what it misses. It promises a next update, not a fix date you don't control.

What you just did

Take a moment with this list, because it's exactly what support engineering interviews ask about:

  • Searched tickets two ways to find the pattern across customers (SQL, ilike, or).
  • Reproduced the bug with an API call and captured a request id (HTTP, headers).
  • Found the log line and read the stack trace down to a line of code.
  • Read unfamiliar code well enough to explain the bug in one sentence.
  • Tied the start of the failures to a specific deploy.
  • Sized the impact from data, already-hit and at-risk (count(distinct …), joins, subqueries).
  • Found a workaround and stated its gap honestly.
  • Wrote for two audiences: the engineer and the customer.
Interview prep

"Tell me about a time you debugged a customer issue" is in nearly every support engineering interview. Tell it in the order of section headings above: what the customer reported, how you reproduced it, what the logs showed, how you found when it started, the impact in numbers, the workaround, and what you handed engineering. You also have real stories from running your own product; tell those the same way.
